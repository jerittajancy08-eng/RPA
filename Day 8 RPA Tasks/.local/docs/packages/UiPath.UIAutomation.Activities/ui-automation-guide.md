## Window Baseline

List open top-level windows/browser tabs **before UIA work** (target open?) and **around workflow runs** (leaks?).

In the snapshot examples throughout this guide, `$WORK_FOLDER` is the directory the CLI writes snapshot artifacts to — your capture work folder (the same one the [`uia-configure-target`](references/uia-configure-target-guide.md) flow sets up in TARGET-1). The CLI creates it if it does not exist.

### List top-level targets

```bash
uip rpa uia snapshot capture --folder-path "$WORK_FOLDER"
```

The command writes the snapshot to a `.yml` file and prints that file's path. **Search the command output for the `.yml` path, then open and read that exact snapshot file before making any window or launch decision.** The window tree and refs come from the YAML contents, not from command success or the path alone.

In the snapshot YAML, windows use `wN`; browser tabs use `bN` nested under their parent:

```
- Window "Untitled - Notepad" [ref=w1]:
  - /process: notepad.exe
- Window "Google Chrome" [ref=w2]:
  - /process: chrome.exe
  - BrowserTab "Example" [ref=b1] [selected]:
    - /url: https://example.com/
```

Missing expected window may be filtered; retry with `--all-windows`.

**Tab/window state markers flag access limits.** Active tab `[selected]`. On a `BrowserTab`:

- `[discarded]` — suspended by the browser to save memory; auto-restores on first interaction.
- `[internal page]` / `[extension store]` / `[file URL]` — page elements not inspectable via `bN` (browser internal pages, web-store pages, local `file://` URLs); target the parent `wN` as a desktop application instead. `[file URL]` is inspectable only when the UiPath extension has "Allow access to file URLs" enabled.

A browser window with no `BrowserTab` child carries the reason on the window itself: `[extension missing]` (UiPath browser extension not installed or disabled) or `[incognito]` (extension not allowed in this private window; enable it in the browser's extension settings). In both cases `wN` still controls the browser as a desktop application.

### Pre-flight (before configuring any target or writing any UIA workflow)

Run the command once, locate its `.yml` output path, and read that file:

- **Present** → run `uia-configure-target`; it attaches.
- **Absent** → launch app, then run `uia-configure-target`; its capture finds new window.

Do not re-snapshot/poll; `uia-configure-target` owns later capture/attach. Pre-flight decides launch only.

**Never infer app state via `Get-Process`, `tasklist`, `ps`, WMI, window-title scraping, or other OS process commands.** They report processes, not UIA-visible windows; background apps/name-mismatched binaries cause wrong launch decisions.

### Diff and close leaked windows (around runs)

Baseline **titles, `/process` values, `/url`s**, not refs. Every top-level `snapshot capture` writes a fresh `window-tree.yml` and re-mints refs; `w1` may identify different windows. After the run, capture again, read the new `window-tree.yml`, then close new title/process/URL entries using refs from that **latest snapshot**:

```bash
uip rpa uia snapshot capture --folder-path "$WORK_FOLDER"  # fresh refs in window-tree.yml
uip rpa uia interact window close w3                       # window leaked by the run
uip rpa uia interact window close b2                       # browser tab leaked by the run
```

Never close via baseline refs; each top-level capture invalidates prior `wN`/`bN`, which may now identify another window.

## Capturing from Manual Test Steps

For Test Manager cases, PDDs, or written "Click/Enter/Select/Verify" steps, capture every interaction target before coding.

1. **Inventory.** Map each `Click`, `Enter`, `Type`, `Select`, `Choose`, `Verify visible`, or `Read` to **one** Object Repository element. Assertions (e.g. "Verify text contains X") require their read element.
2. **Group by screen state.** Current batch ends at UI advance (submit, navigation, dialog confirmation); next starts after it.
3. **Build checklist:** `manual step → element name → screen`. Lock count before app launch. Later requirements add capture deltas; do not re-inventory.
4. **Capture per screen:** Window Baseline pre-flight → `uia-configure-target` current batch → register every element → advance via UIA interact CLI → repeat. Mandatory Complete-then-advance: [references/uia-configure-target-guide.md § Multi-Step UI Flows](references/uia-configure-target-guide.md). Never advance with unregistered elements.
5. **Code.** After all rows register, author `.cs`/`.xaml` in step order. Run authoring prerequisites/project discovery now, not earlier.

> Coverage gate: every row needs `Descriptors.<App>.<Screen>.<Element>` (coded) or Object Repository reference (XAML). Unmatched row = missed capture/obsolete step; reconcile before coding.

## Terminology — what "screen" means

"Screen" has three independent meanings:

| Sense | Used in | What it is | Boundary / identity |
|-------|---------|------------|---------------------|
| **Capture screen** | XAML Multi-Screen Authoring (below), [references/uia-configure-target-guide.md § Multi-Step UI Flows](references/uia-configure-target-guide.md) | Distinct UI state requiring its own `uia-configure-target` pass because app must be advanced (via `uip rpa uia interact` CLI) between captures. | Bounded by app advancement — everything captured before next advance is one capture screen. |
| **Object Repository screen** | Object Repository CLI, `.objects/` layout, `Descriptors.<App>.<Screen>.<Element>`, [references/uia-configure-target-guide.md](references/uia-configure-target-guide.md) | Data-model entity in Object Repository, registered and matched via Object Repository CLI. | Identified by its window selector. |
| **Screen handle** (coded only) | "Screen Handle Affinity" under § For Coded Workflows | Runtime `UiTargetApp` returned by `uiAutomation.Open` / `Attach`, bound to one Object Repository screen. | Element descriptors valid only on the handle for their own Object Repository screen. |

Multiple capture screens can share one Object Repository screen/window selector (e.g. URL-neutral tab selector). One Object Repository screen can yield many runtime handles (one per `Open`/`Attach`).

**XAML Multi-Screen Authoring uses capture-screen.** "2 or more distinct screens" = 2 or more UI states requiring separate captures, independent of Object Repository entry count.

## Mandatory: Generate Targets Before Writing Any UI Code

Before ANY C# (`uiAutomation.Open(...)`, `Descriptors.App.Screen.Element`) or XAML (`<uix:TargetApp>`, `<uix:TargetAnchorable>`) target:

1. **NEVER hand-write selectors.** Risks: invalid syntax/attributes, missing `SearchSteps`/`ContentHash`/`Reference`, wrong element; validation/runtime failure.
2. **NEVER infer attributes** from HTML/DOM, tags, or CSS. Generate by probing live UI tree, not source inspection.
3. **ALWAYS follow** [references/uia-configure-target-guide.md](references/uia-configure-target-guide.md). Before registration, only `uia-configure-target` may transform definitions via documented CLI commands; never hand-edit definitions, content hashes, or reference IDs. Consumers attach returned final artifacts unchanged.
4. **NEVER replace UIA with external browser automation.** For requested UiPath RPA, PowerShell, Selenium, Playwright, Chrome DevTools Protocol, raw DOM JavaScript, HTTP form posts, and `InvokeCode` may serve non-UI setup/diagnostics/data preparation only. Visible interaction requires UIA activities or coded `uiAutomation` with Object Repository descriptors.
5. **Explore through UiPath UIA.** Use UI Automation skills, snapshot CLI, `uia-configure-target`, `uip rpa uia interact`, and Object Repository capture for app/window/UI/selector discovery and capture. Syntax: [§ Window Baseline](#window-baseline), [§ Advancing UI State](#advancing-ui-state), [references/input-methods-guide.md](references/input-methods-guide.md), [references/select-item-usage-guide.md](references/select-item-usage-guide.md), [references/get-text-usage-guide.md](references/get-text-usage-guide.md), and top CLI-discovery note. Never use Playwright, Selenium, DOM inspection, process lists, or ad hoc scripts to choose targets/selectors.
6. **Use modern CV/semantic targets when selectors are not viable.** If strict/fuzzy selectors cannot be configured or validated, keep the modern `TargetAnchorable` flow and set `SearchSteps` to `TargetSearchSteps.CV` for visual matching or `TargetSearchSteps.SemanticSelector` for natural-language matching. RDP/VDI/Citrix often need CV; semantic selector is also valid when the element can be described clearly. Use modern activities/coded `UiTargetApp` methods; do not look for or recommend classic CV packages or activities (`UiPath.CV.Activities`, `UiPath.ComputerVision.Activities`, `CVScope`, `CvClick*`, `CvTypeInto*`) for new automation.

> Gate applies to every target. Even `<webctrl tag='BODY' />` fails without required attributes. Configure instead of debugging fabricated selectors.

Anchors require `FuzzySelector`; `add-anchor` atomically converts strict `Selector` before attachment. Failure stops registration.

### Don't override a step whose purpose is to replace your judgment

Ground-truth checks cannot be replaced by judgment: doing so leaves decisions unverified and risks expensive silent errors. Compress narration/redundant round-trips, never correctness steps.

## Common UIA Pitfalls

- **SelectItem vs click-to-open** — support is independent of UI stack/tag/role; native `<select>`, WinForms/WPF combo, Java/SAP list, and ARIA combobox are candidates. Query `items` via interact CLI: options → `SelectItem` with listed value, no option capture; empty/absent → click-to-open + click-option (or `TypeInto`). [references/select-item-usage-guide.md](references/select-item-usage-guide.md).
- **Confirm what `Get Text` extracts before authoring** — don't judge from a screenshot, and don't wait for a bad result ([§ Reading Values from the UI](#reading-values-from-the-ui)). Empty/partial text usually means the wrong `--scraping-method` (`TextAttribute`/`Fulltext`/`Native`/`OCR`), not a broken target/selector; a non-empty value on an element with no content is the inverse trap. Also consider `Get Attribute`/`NGetAttribute` for a cleaner, structured value. [references/get-text-usage-guide.md](references/get-text-usage-guide.md).
- **ScreenPlay overuse** — UITask/ScreenPlay is non-deterministic and slow. Always try proper selectors first.
- **Wrong Object Repository references** — never copy references from examples or other projects. Always use `uia-configure-target` to generate them for current application state.
- **`InjectJsScript` replacing standard activities** — do NOT use when configured-target GetText, Click, TypeInto, ExtractTableData, etc. work. Last resort: hard to debug, page-fragile, bypasses Object Repository.
- **Invented keyboard shortcuts replacing targets** — do NOT substitute `Ctrl+S`, `Alt+F4`, `Tab`, menu mnemonics, etc. for real click/type targets. Configured `Click`/`TypeInto` are deterministic, layout-resilient, logged; guessed shortcuts depend on focus/locale/version. Use only genuinely hotkey-only commands with no clickable surface, confirmed live; never infer from convention.
- **Multiple `NKeyboardShortcuts` keystrokes after navigation hit stale nodes.** Activity resolves `Target` once. If first shortcut replaces it, another shortcut in same `Shortcuts` string or via `DelayBetweenShortcuts` throws `InvalidNodeException: "The UI element is invalid..."`. Example: Explorer "Items View" `Alt+Up` navigates (auto-selecting current folder) and destroys node; chained `Alt+Enter` faults. **Fix:** separate `NKeyboardShortcuts` activities so follow-up re-resolves on new screen; add small `DelayBefore` for settling.
- **Selector resolves but interaction faults** — prior interaction may remount target (e.g. click-before-type or popup expansion), leaving detached node and `UI element is invalid`. Diagnose/fix: [references/uia-elements-interaction-guide.md § Debugging a failed interaction with an element](references/uia-elements-interaction-guide.md).
- **Unnecessary pre-UIA `Delay`** — `NClick`, `NTypeInto`, `NSelectItem`, `NGoToUrl`, etc. retry selector lookup until configurable timeout. Add `Delay` only when ALL hold: wait is not for UI targeted by next UIA activity; non-retry reason exists (unanchored animation, fixed business pause, UI-invisible background job); caller can explain why built-in retry fails. Async-disabled present buttons are different: use activity `DelayBefore`/`DelayAfter`, not `Delay`. [references/uia-elements-interaction-guide.md § Buttons disabled during async operations](references/uia-elements-interaction-guide.md).
- **`Cannot send input ... outside of screen bounds` on hover-revealed elements** — popup items, autocomplete entries, and dropdown rows may fail with default input. Switch activity/interact counterpart to simulated input. [references/input-methods-guide.md](references/input-methods-guide.md).
- **Workflow left on default input despite proven `Simulate`/`DebuggerApi` support** — carry the method proven during interact driving into card/activity `InteractionMode`. [references/input-methods-guide.md § Carry the proven method into the workflow](references/input-methods-guide.md#carry-the-proven-method-into-the-workflow).
- **[macOS] Menu-bar click silently no-ops under `Simulate`** — `Simulate` never activates the target app, on any platform, by design; fine for controls (accessibility APIs need no foreground), but AppKit validates menu-item enablement against the app's responder chain, and an inactive app has no first responder — so the menu opens and responder-dependent items (Notes `File ▸ Pin Note`) report `disabled` with no error raised. Add `NWindowOperation` `Operation="ToForeground"` before menu-bar clicks; `ActivateBefore` will not do it.
- **`HealingAgentBehavior` enums differ.** `NApplicationCard` accepts `NHealingAgentBehavior`: `Job`, `Disabled`, `RecommendationOnly`. Children (`NClick`, `NTypeInto`, `NCheckState`, etc.) use `NChildHealingAgentBehavior`, adding `SameAsCard`. Card `SameAsCard` fails: `Failed to create a 'HealingAgentBehavior' from the text 'SameAsCard'`. New cards must use card values, never copied child value. [activities/common/NHealingAgentBehavior.md](activities/common/NHealingAgentBehavior.md), [activities/common/NChildHealingAgentBehavior.md](activities/common/NChildHealingAgentBehavior.md).
- **Per-item target in a loop matches wrong/stale node** — activity run once per loop item must pin the item's varying value on the item/row selector via the loop variable; an upstream search/filter does not guarantee a single runtime match (stale panes, variant duplicates, async repopulation). [references/selector-variables.md § When to parametrize](references/selector-variables.md#when-to-parametrize-per-item-actions-in-a-loop).

## Control-Specific Interaction Patterns

> **MANDATORY before `TypeInto`, `SelectItem`, or `Click`** (XAML `NTypeInto`/`NSelectItem`/`NClick`; coded `uiAutomation.*`): classify captured control. For any date/time input, dropdown, or async-disabled button, read/apply [references/uia-elements-interaction-guide.md](references/uia-elements-interaction-guide.md) IN FULL before authoring, like [§ Configuring Targets](#configuring-targets-object-repository). Use displayed date format (not ISO) through key events; choose dropdown method from interact CLI `items`, not tag/role; use `DelayBefore` for async-disabled buttons. Never guess then iterate live.

After capture:

- **Date / formatted date-time inputs** — type the field's **displayed** format (e.g. en-US `MM/DD/YYYY`), not the ISO `value`.
- **Dropdowns / lists / comboboxes** — query control's `items` attribute (via interact CLI); items listed → `SelectItem`, none → click-to-open + click option (or `TypeInto`). Independent of tag / role / UI technology.
- **Buttons disabled during async ops** — present but `disabled` during validation/load/refresh; use activity's `DelayBefore`/`DelayAfter` properties (not a `Delay` activity).

Guide covers web date inputs and cross-technology dropdowns/lists/async-disabled buttons.

## Configuring Targets (Object Repository)

First read [references/uia-configure-target-guide.md](references/uia-configure-target-guide.md) IN FULL: workflow, rules, indication fallback, multi-step flows.

### Multi-Step UI Flows (Advancing Application State)

Procedure: [references/uia-configure-target-guide.md § Multi-Step UI Flows](references/uia-configure-target-guide.md) — capture loop and Complete-then-advance rule.

### Advancing UI State

Advance live UI with `uip rpa uia interact` between captures or to reveal elements. `interact` is stateless: each verb performs one action and leaves resulting state.

**Reuse refs.** `uia interact` resolves `wN`/`bN`/`eN`/`sN` from **latest snapshot regardless of producer**: `uia snapshot` or a `uia-configure-target` capture. If UI is unchanged, reuse refs; re-capturing is wasted work.

After advance, old e-refs are stale and may silently resolve to newly numbered elements. Before new-state interaction, make sure your refs come from a snapshot taken after the advance.

**Choose input method deliberately** — prefer `DebuggerApi` (Chromium) / `Simulate` over the `HardwareEvents` default. Each advance doubles as a live support probe: the proven method becomes the workflow's `InteractionMode` (card-level; per-activity override for exceptions). [references/input-methods-guide.md](references/input-methods-guide.md).

Use every required verb (e.g. menu then item; type then Enter):

```bash
# Single-step advance: click the button that opens the next screen
uip rpa uia interact click e28

# Type then confirm with Enter (special-key syntax, same encoding as Type Into's Text)
uip rpa uia interact type e5 "invoice 4711"
uip rpa uia interact type e5 "[k(enter)]"

# Modifier shortcuts: clear the field (Ctrl+A then Delete), then paste
uip rpa uia interact type e5 "[d(ctrl)]a[u(ctrl)][k(del)]"
uip rpa uia interact type e5 "[d(ctrl)]v[u(ctrl)]"

# Tab through several fields in one call
uip rpa uia interact type e5 "line1[k(tab)]line2[k(tab)]line3"

# macOS: primary modifier is Command (⌘), Option (⌥) replaces Alt — write the token explicitly (no auto-conversion)
uip rpa uia interact type e5 "[d(command)]a[u(command)][k(del)]"   # ⌘A then Delete (clear field)
uip rpa uia interact type e5 "[d(option)][k(right)][u(option)]"    # ⌥→ move one word right

# Multi-step advance: open a menu, re-capture to see the submenu, click the item
uip rpa uia interact click e13
uip rpa uia snapshot capture --folder-path "$WORK_FOLDER" --definition-file-path "$WORK_FOLDER/window.xaml"
uip rpa uia interact click e42
```

`$WORK_FOLDER/window.xaml` above is the window definition produced during capture & `target-app resolve-defaults` (see [Configure Target Guide](references/uia-configure-target-guide.md) and `uia-configure-target` TARGET-2) — passing it scopes the re-capture to that window. It is not a file you hand-author.

Other advances: `select` (option), `hover` (reveal), `wheel` (scroll), `focus`, `interact window foreground/maximize/...`, and web `interact browser` (`navigate`, `tab-new`, `tab-select`, `go-back`, ...).

For advanced/SAP verbs, modifiers, input methods, click types/offsets, drag-and-drop, and full key/token encoding: grep `^##` in [references/cli-reference.md](references/cli-reference.md), read `interact` section, run `<command> --help`.

Before new-state actions, confirm via window re-capture (fresh tree/refs) or `interact screenshot w1`.

## For Coded Workflows

**Service accessor:** `uiAutomation` (type `IUiAutomationAppService`)

Coded-specific API: [coded/coded-api.md](coded/coded-api.md).

### Workflow Pattern

1. **Open/Attach** application screen; receive `UiTargetApp`.
2. Use handle for Click, TypeInto, GetText, etc.
3. `UiTargetApp` is `IDisposable`; dispose via `using` or manually.

### Screen Handle Affinity (Critical)

> Here, "screen" means **Object Repository screen** (`Descriptors.<App>.<Screen>.<Element>`), not capture screen (§ Terminology).

**Each `UiTargetApp` binds one Object Repository screen.** Descriptors require their screen's handle; Screen A descriptor on Screen B handle fails: `"Target name 'X' is not part of the current screen."`.

```csharp
// CORRECT — use Home elements on the homeScreen handle
var homeScreen = uiAutomation.Open(Descriptors.MyApp.Home);
homeScreen.Click(Descriptors.MyApp.Home.Products);   // OK

// Then attach to the next screen for its elements
var formScreen = uiAutomation.Attach(Descriptors.MyApp.Form);
formScreen.TypeInto(Descriptors.MyApp.Form.Email, "test@example.com");  // OK

// WRONG — using a Home element on the Form screen handle
formScreen.Click(Descriptors.MyApp.Home.Loans);  // FAILS
```

In multi-screen flows, finish one screen before attaching next.

### Target Resolution

`UiTargetApp` methods accept:
- **`string target`** — target name defined in the Object Repository screen.
- **`IElementDescriptor elementDescriptor`** — strongly-typed Object Repository descriptor (e.g., `Descriptors.MyApp.LoginScreen.Username`).
- **`TargetAnchorableModel target`** — via the `UiTargetApp` indexer: `app["targetName"]` or `app[Descriptors.MyApp.Screen.Element]`.
- **`RuntimeTarget target`** — runtime target returned by `GetChildren` or `GetRuntimeTarget`.

### Finding Descriptors (Mandatory)

**MANDATORY for `uiAutomation.*`:** follow strict order; stop at first matching descriptor.

> **CRITICAL:** Steps 1 → 2 → 3 → 4 MUST be followed sequentially. NEVER skip to Step 4 (UITask).

#### Step 1 — Check the project's Object Repository

Read `<PROJECT_DIR>/.local/.codedworkflows/ObjectRepository.cs`: `Descriptors` class with `Descriptors.<App>.<Screen>.<Element>` hierarchy.

> **Generation requires Studio Desktop.** It regenerates `ObjectRepository.cs` only after detecting `.cs` with `[Workflow]`/`[TestCase]` and reconciling Object Repository; `uip rpa build` alone does NOT. If missing/stale after registration:
> 1. Confirm Studio Desktop is running against the project (start with `uip rpa studio start --project-dir "<PROJECT_DIR>"` if needed).
> 2. Ensure at least one coded-workflow `.cs`; Studio triggers only for a coded surface needing descriptors.
> 3. Save/re-open project in Studio Desktop to force regeneration.
>
> Pure CLI without Studio Desktop cannot produce `ObjectRepository.cs`; workflows using `Descriptors.*` need Studio Desktop.

If missing/stale, enumerate saved registered apps/screens/elements without regeneration: `uip rpa object-repository get --project-dir "<PROJECT_DIR>" --output json`. Confirm existence before authoring; strongly typed `Descriptors.<App>.<Screen>.<Element>` still requires `ObjectRepository.cs`.

Add Object Repository namespace:
```csharp
using <ProjectNamespace>.ObjectRepository;
```

#### Step 2 — Check UILibrary NuGet packages

Check `project.json` `dependencies` for `*.UILibrary`, `*.ObjectRepository`, `*.Descriptors`, `*.UIAutomation`; inspect via `uip rpa packages inspect`.

List library-exposed apps/screens/elements (not merely assembly API) from its `.nupkg` Object Repository: run `uip rpa object-repository get-library --output json`, pointing at library `.nupkg` path(s).

For UILibrary, use **package**, not project, namespace:
```csharp
using <PackageNamespace>.ObjectRepository;
```

#### Step 3 — Configure the target

[references/uia-configure-target-guide.md](references/uia-configure-target-guide.md) MUST be read IN FULL first.

After completion, re-read `ObjectRepository.cs`; search returned reference IDs for exact `Descriptors.<App>.<Screen>.<Element>` paths.

#### Step 4 — UITask / ScreenPlay (last resort only)

ScreenPlay (`UITask`) performs AI UI interactions without precise selectors. Use **only** when Step 3 selectors are genuinely unreliable.

### Coded-Specific Pitfalls

- **Missing ObjectRepository using** — without `using <ProjectNamespace>.ObjectRepository;`: `CS0103: The name 'Descriptors' does not exist in the current context`
- **Screen handle mismatch** — element descriptor on wrong screen handle causes `"Target name 'X' is not part of the current screen."` Always use the correct handle for each screen's elements.

### Multi-Screen Authoring

> Here, "screen" means **capture screen** (§ Terminology): UI state requiring separate `uia-configure-target` pass after app advance, not Object Repository screen. One Object Repository entry can still represent multiple capture passes separated by `uip rpa uia interact` advances.

Honor caller ordering: capture-first tasks defer authoring until all targets register; otherwise add activities per capture screen as references arrive. Keep UI activities in `NApplicationCard`; validate each batch. First read [references/uia-configure-target-guide.md](references/uia-configure-target-guide.md) IN FULL.

### Key Concepts

#### Application Card (Use Application/Browser)

Every workflow starts with **Application Card** (`uix:NApplicationCard`) opening/attaching desktop app or browser; all Click, TypeInto, GetText, etc. belong inside. Card has no app `FilePath`/URL; linked `TargetApp` identifies app ([§ Target Configuration](#target-configuration)).

> **Default: ONE card per attached application instance.** `ByInstance` covers main window, dialogs, popups, menus, and owned children. Add/nest for another instance/application/process or proven `ByInstance` failure; never per window/dialog/Object Repository screen.

##### Window Attach Mode

`AttachMode` (`NAppAttachMode`, default `ByInstance`) controls inner target search. Change per [activities/ApplicationCard.md](activities/ApplicationCard.md).

**`ByInstance` — Application Instance (default/preferred).** Finds selector window; attaches ALL instance windows (main/dialogs/children). Each activity uses its **scope selector** to choose instance window, then searches inside.

Use for separate same-instance windows (e.g. dialogs); one card covers all via activity scope selectors.

```xml
<uix:NApplicationCard AttachMode="ByInstance" DisplayName="Use App (Invoice app)"
                      sap2010:WorkflowViewState.IdRef="NApplicationCard_1" Version="V2">
    <uix:NApplicationCard.Body>
        <Sequence sap2010:WorkflowViewState.IdRef="Sequence_1">
            <!-- scope selector targets the main window -->
            <uix:NClick DisplayName="Click New Invoice" sap2010:WorkflowViewState.IdRef="NClick_1" />
            <!-- scope selector targets the dialog window of the same instance -->
            <uix:NTypeInto DisplayName="Type amount in dialog" Text="[in_Amount]"
                           sap2010:WorkflowViewState.IdRef="NTypeInto_1" />
        </Sequence>
    </uix:NApplicationCard.Body>
</uix:NApplicationCard>
```

**`SingleWindow` — narrower fallback only after demonstrated `ByInstance` failure.** Attaches only selector window; cannot find same-instance parent/child/dialog targets and always ignores activity scope selectors.

```xml
<uix:NApplicationCard AttachMode="SingleWindow" DisplayName="Use App (single window)"
                      sap2010:WorkflowViewState.IdRef="NApplicationCard_2" Version="V2">
    <uix:NApplicationCard.Body>
        <Sequence sap2010:WorkflowViewState.IdRef="Sequence_2">
            <!-- only targets in THIS window resolve; scope selector is ignored -->
            <uix:NClick DisplayName="Click Save" sap2010:WorkflowViewState.IdRef="NClick_2" />
        </Sequence>
    </uix:NApplicationCard.Body>
</uix:NApplicationCard>
```

##### One application instance = one card (even with multiple Object Repository screens)

Object Repository creates **screen** per distinct window selector (e.g. titled dialog/popup/child), not card: **Object Repository screens != Application Cards.** Window selectors determine screens; attached application instances determine cards. Matching `app=` signals compatibility, not instance identity.

`ByInstance` hosts activities across same-instance Object Repository screens. Each scope selector finds its window within instance; card selector need not match every screen. Owned dialogs/popups validate/run under one card without dedicated cards or "indicated element does not belong to the target application/browser" errors.

Concrete MS Paint File ▸ Open ▸ Cancel example: [§ Same-Instance Secondary Windows](#same-instance-secondary-windows--reuse-the-card-do-not-nest).

Never nest for second Object Repository screen or "scope/selector alignment"; `ByInstance` aligns via activity scope selector. Add card only after [escalation gate below](#nesting-application-cards).

##### Nesting Application Cards

> **Nest for another instance/application/process** (e.g. App A -> App B). Same-instance windows use one `ByInstance` card ([§ One application instance = one card](#one-application-instance--one-card-even-with-multiple-object-repository-screens)); nest same instance only after proven attach/find failure, never for another Object Repository screen.

Cards nest; activity can target any card on parent chain. For two-app switching, nest cards, place all activities in innermost, attach each to correct card.

`ScopeIdentifier` selects exact card `ScopeGuid`; omission selects nearest applicable card. Activity target must match selected card, not lexical ancestors. Attachment: [activities/ApplicationCard.md](activities/ApplicationCard.md).

**IMPORTANT:** Only configured-target activities may have `ScopeIdentifier`; never add it without target.

Example: App A outer, App B inner; both activities live inner. Read uses A `ScopeGuid`; write uses B. Repeat switching without card re-entry.

```xml
<uix:NApplicationCard AttachMode="ByInstance" DisplayName="App A (source)"
                      ScopeGuid="aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa"
                      sap2010:WorkflowViewState.IdRef="NApplicationCard_1" Version="V2">
    <uix:NApplicationCard.Body>
        <Sequence sap2010:WorkflowViewState.IdRef="Sequence_1">
            <uix:NApplicationCard AttachMode="ByInstance" DisplayName="App B (target)"
                                  ScopeGuid="bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb"
                                  sap2010:WorkflowViewState.IdRef="NApplicationCard_2" Version="V2">
                <uix:NApplicationCard.Body>
                    <Sequence sap2010:WorkflowViewState.IdRef="Sequence_2">
                        <!-- ScopeIdentifier = App A card's ScopeGuid → reads from App A (outer) -->
                        <uix:NGetText DisplayName="Get value from App A" TextString="[out_Value]"
                                      ScopeIdentifier="aaaaaaaa-aaaa-aaaa-aaaa-aaaaaaaaaaaa"
                                      sap2010:WorkflowViewState.IdRef="NGetText_1" Version="V5" />
                        <!-- ScopeIdentifier = App B card's ScopeGuid → pastes into App B (inner) -->
                        <uix:NTypeInto DisplayName="Type value into App B" Text="[out_Value]"
                                       ScopeIdentifier="bbbbbbbb-bbbb-bbbb-bbbb-bbbbbbbbbbbb"
                                       sap2010:WorkflowViewState.IdRef="NTypeInto_1" Version="V5" />
                    </Sequence>
                </uix:NApplicationCard.Body>
            </uix:NApplicationCard>
        </Sequence>
    </uix:NApplicationCard.Body>
</uix:NApplicationCard>
```

> GUIDs are placeholders. Generate card `ScopeGuid` via `uip rpa activities get-default-xaml` starter `NApplicationCard`; never hand-author. Set `ScopeIdentifier` to target card `ScopeGuid`. Keep GUIDs unique: unmatched usually fails at runtime; duplicate may bind wrong card. Validation may miss either.

##### Cross-Process Helper Dialogs (Sign-in, OAuth, System Pop-ups)

Some sign-in/consent/system dialogs spawn **separate processes**:

- Microsoft Store sign-in opens in `WWAHost.exe` (not `WinStore.App.exe`)
- Office desktop sign-in / Microsoft Account flows hosted in `WWAHost.exe` or `Microsoft.AAD.BrokerPlugin`
- OAuth pop-ups launched by an enterprise app into the system browser
- Save / Open / Print / UAC dialogs hosted by `consent.exe`, `dllhost.exe`, etc.

Helper-process activity inside original-app card fails validation:

```
The indicated element does not belong to the target application/browser.
```

Validator compares child `ScopeSelectorArgument` to selected card `TargetApp`; different `app=` always triggers error despite correct runtime selectors.

> **Identify attachment boundary.** Different `app=` requires another card; matching `app=` passes validation but does not prove same runtime instance. Reuse only confirmed same instance; otherwise add card. Top-level-window status adds none.

##### Same-Instance Secondary Windows — Reuse the Card (Do NOT Nest)

Most dialogs/property sheets/popups/children, including Win32 `#32770` Open/Save/Print/Properties, belong to same instance: same `app=`, different `cls=`/`title=`. Reuse its card; another instance needs another card.

Default `AttachMode="ByInstance"` attaches whole instance. Child `ScopeSelectorArgument` finds target window, including dialog when card `TargetApp` names main window. Second same-instance card adds only scope ([§ One application instance = one card](#one-application-instance--one-card-even-with-multiple-object-repository-screens)).

Matching child/card `app=` passes compatibility validation; difference triggers "does not belong...". Passing does not establish instance attachment.

**MS Paint File ▸ Open ▸ Cancel:** *Open* creates top-level Win32 `#32770`, captured as separate Object Repository screen in same attached Paint instance. Cancel `ScopeSelectorArgument`: `<wnd app='mspaint.exe' cls='#32770' title='Open' />`; card `TargetApp`: `<wnd app='mspaint.exe' cls='MSPaintApp' title='*Paint*' />`. `ByInstance` spans File/Open/Cancel; neither File menu nor dialog needs another card. Matching `app=` passes compatibility validation.

Use nested pattern for another attached instance/application/process or proven `ByInstance` failure.

##### Pattern: Nest a Second `NApplicationCard` for the Helper Process

Wrap helper-process activities in helper-scoped `NApplicationCard`. One card may span same-instance subdialogs using `uia-configure-target` CLI-stabilized/evaluated `title='*'`. Never hand-edit returned XAML; example shows final artifact.

```xml
<!-- Outer: original app -->
<uix:NApplicationCard ScopeGuid="<outer-guid>" Version="V2" HealingAgentBehavior="Job" ...>
  <uix:NApplicationCard.TargetApp>
    <uix:TargetApp Selector="&lt;wnd app='WinStore.App.exe' title='Microsoft Store' /&gt;" Version="V3" />
  </uix:NApplicationCard.TargetApp>
  <uix:NApplicationCard.Body>
    <ActivityAction x:TypeArguments="x:Object">
      <ActivityAction.Argument>
        <DelegateInArgument x:TypeArguments="x:Object" Name="WSSessionData" />
      </ActivityAction.Argument>
      <Sequence>
        <!-- Activity that triggers the helper-process launch (still in outer scope) -->
        <uix:NClick ScopeIdentifier="<outer-guid>" ... DisplayName="Click Sign In" ... />

        <!-- Inner: helper process (nested card) -->
        <uix:NApplicationCard ScopeGuid="<inner-guid>" Version="V2" HealingAgentBehavior="Job" ...>
          <uix:NApplicationCard.TargetApp>
            <uix:TargetApp Selector="&lt;wnd app='WWAHost.exe' title='*' /&gt;" Version="V3" />
          </uix:NApplicationCard.TargetApp>
          <uix:NApplicationCard.Body>
            <ActivityAction x:TypeArguments="x:Object">
              <ActivityAction.Argument>
                <DelegateInArgument x:TypeArguments="x:Object" Name="WSSessionDataInner" />
              </ActivityAction.Argument>
              <Sequence>
                <!-- Activities here use ScopeIdentifier="<inner-guid>" -->
                <uix:NTypeInto ScopeIdentifier="<inner-guid>" ... />
                <uix:NClick   ScopeIdentifier="<inner-guid>" ... />
              </Sequence>
            </ActivityAction>
          </uix:NApplicationCard.Body>
        </uix:NApplicationCard>

        <!-- Back in outer scope after the helper closes -->
        <uix:NCheckState ScopeIdentifier="<outer-guid>" ... DisplayName="Verify Signed In" ... />
      </Sequence>
    </ActivityAction>
  </uix:NApplicationCard.Body>
</uix:NApplicationCard>
```

**Rules:**

1. **One card per attached instance, not window.** Another instance/application/process needs another card; same-instance windows share one `ByInstance` card. Top-level status adds none.
2. **Target selected card.** `ScopeIdentifier` chooses exact `ScopeGuid`; omission chooses nearest card. Update when moving activity. Keep GUIDs unique; validation may miss unmatched/duplicate values.
3. **Card-level `HealingAgentBehavior`** uses `NHealingAgentBehavior` (`Job`/`Disabled`/`RecommendationOnly`) — not `SameAsCard` (see [§ Common UIA Pitfalls](#common-uia-pitfalls)).
4. **Use helper-card `title='*'`** only for multiple same-instance subdialogs, after CLI stabilization and evaluation. Stable titles improve selectors but never determine card count.

Capture helper targets per [references/uia-configure-target-guide.md § Capturing Targets for Helper Processes](references/uia-configure-target-guide.md).

#### Target Configuration

First read [references/uia-configure-target-guide.md](references/uia-configure-target-guide.md) IN FULL; register card screen and activity elements. Then write plain NApplicationCard/NClick/NTypeInto/... with unique `sap2010:WorkflowViewState.IdRef`, no `.Target` children; attach via [references/uia-target-attachment-guide.md](references/uia-target-attachment-guide.md).

Never hand-write `<uix:TargetApp>`/`<uix:TargetAnchorable>`; attach per [references/uia-target-attachment-guide.md](references/uia-target-attachment-guide.md).

A CV-resolved target is still an ordinary `TargetAnchorable` (`SearchSteps=CV`) and attaches via the `.Target` property to any activity that supports a target (e.g. `NClick`, `NGetText`, `NTypeInto`), like any other target. Never switch to the legacy `UiPath.CV.Activities` package for CV-resolved elements — it bypasses the Object Repository and is a separate, unsupported model here.
